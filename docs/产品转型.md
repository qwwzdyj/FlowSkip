## 一、转型起因

第三阶段末读完赛道完整说明后，识别出 FlowSkip 当前产品命题与赛道命题**方向不一致**。前三阶段在做项目设计时未对照赛道说明（自查疏忽）。本文档记录诊断、决策、新 MVP 与剩余 10 小时的执行计划。

---

## 二、赛道命题摘要

赛道：**Agent-Pilot · 从 IM 对话到演示稿的一键智能闭环**。

- **作品形态**：从 IM 自然语言指令开始，Agent 拆解任务并自动驱动 Doc、PPT/画布、多端汇报的**端到端工作流**
- **核心理念**：Agent 是主驾驶（Pilot），GUI 是仪表盘 + 精细调整面板（Co-pilot）
- **必须项**：
  1. **多端协同框架**（移动 iOS/Android + 桌面 macOS/Windows，实时双向同步）
  2. **6 个场景模块**：意图入口（IM）/ 规划 / Doc / PPT 或画布 / 多端一致性 / 总结交付
  3. **覆盖 IM + Doc + (PPT 或自由画布)**
  4. **自然语言交互**（文本或语音，至少其一）
- **加分项**：离线 / Agent 主动澄清 / 富媒体画布操作 / 第三方平台集成（飞书等）
- **演示验收**：多端切换、IM 自然语言触发 Agent 编排、IM/Doc/PPT 三件套串联

---

## 三、错位诊断

| 维度 | 赛道要求 | FlowSkip 原设计 | 状态 |
|---|---|---|---|
| **核心命题** | 单用户的 IM→Doc→PPT 工作流自动化 | 多人分身减少协同沟通熵 | **方向不一致** |
| IM 入口 | 必须 | 已设计 | ✅ |
| LLM 任务规划 | 必须 | 已设计（分身意图解析） | ✅ |
| 文档生成/编辑 | 必须 | 仅"写回飞书文档" | ⚠️ 弱 |
| **PPT/自由画布** | **必须二选一** | 完全没有 | ❌ 缺 |
| **多端(移动+桌面)** | **必须** | 单后端，无客户端 | ❌ 缺 |
| **GUI 仪表盘** | **必须**(Co-pilot) | 完全没有 | ❌ 缺 |
| 自然语言(文本/语音) | 必须 | 文本 ✅、语音无 | ⚠️ 部分 |

**直白结论**：赛道命题是"做一个个人 Agent 助理，把 IM 需求一键变成 PPT"；原 FlowSkip 命题是"做一个团队减摩擦工具，让分身互相对齐字段需求"。**这不是同一个产品**。前三阶段 2300+ 行 planning 主要在打"多人协同"的地基，而赛道核心几个必须项（PPT、多端、GUI）我们零基础。

## 四、转型决策

**采用方向 C（混合）**：保留 FlowSkip 的多 Agent 架构，**重新定位为"为单用户服务的专业 Agent 团队"**。

语义重解释：
- "分身协同"从 **"多人协同代理"** 重新定义为 **"为单用户服务的多领域 Agent 协同"**
- A2A 协议、加权 RAG、Twin 抽象、决策与暂缓记录的工程结构**全部保留**
- 产品场景从"产品改字段时多人对齐"改为"产品经理提需求，多专业 Agent 协同生成方案 + Doc + PPT"

**为什么是方向 C 而不是 A 或 B**：
- A（守住原命题）：补 PPT + 多端 + GUI 三个零基础模块在 10 小时内极重，且命题距离大评审仍可能扣分
- B（彻底重做）：放弃 stage 2 的 2300 行 planning 太可惜，飞书接入也要重排
- C：A2A / Twin / RAG 工程基础全部能复用，只换产品场景与交付物形态，性价比最高

## 五、新 MVP 场景

**场景**：产品经理在飞书 IM 提出 **"改一个字段"** 的需求，触发 Agent 编排：

```
[产品经理] ──IM 自然语言──→ [产品经理分身 Agent]
                                  │ 解析需求 + 任务拆解
                                  ▼
                  ┌───────────────A2A───────────────┐
                  ▼                                 ▼
          [设计师分身 Agent]              [软件工程师分身 Agent]
          - 评估视觉/交互影响              - 评估技术可行性 / 改动成本
          - 产出设计建议                   - 产出迁移方案
                  │                                 │
                  └───────────A2A 汇总──────────────┘
                                  ▼
                          [产品分身整合]
                                  │
                  ┌───────────────┴───────────────┐
                  ▼                                 ▼
          [设计文档]                        [PPT 汇报稿]
          for 人 + coding agent             for 会议汇报
```

两份交付物：

- **设计文档**（写入飞书 Doc）：规约 + 改动点清单 + 接口定义 + 数据迁移方案；目标读者是开发同学和后续的 coding agent
- **PPT 汇报稿**：整个沟通过程 + 最终方案 + 关键决策点；用于会议汇报

**这一场景精确匹配赛道核心**：IM 入口 → Agent 拆解协同 → Doc 生成 → PPT 生成 → 多端汇报。

## 六、关键风险与应对

### 6.1 多端协同 = 飞书 IM 双端 (Calculated Bet)

**判断**：移动端和桌面端都用飞书 IM 交互，即视为多端。

**支持点**：
- 飞书 IM 在 iOS / Android / macOS / Windows 都有官方客户端，实时双向同步是飞书自带的
- 飞书 Doc / 演示文稿 也是天然多端同步
- 用户体验上确实是"一端操作，另一端实时可见"
- 加分项明确认可"第三方平台集成"，且赛道说明里写"若选择从零开始，则考察更底层的架构设计能力"——反向暗示用平台是合规的

**加固方案（stretch goal，时间允许时做）**：**额外做一个飞书消息卡片仪表盘**作为 Co-pilot GUI：

- 用飞书 [interactive card](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/feishu-cards) 做 Agent 编排进度可视化（任务列表 + 各 Agent 状态 + 实时输出片段）
- 用户可在卡片上点击"批准 / 调整 / 重做"按钮影响 Agent 流程
- 这个卡片在飞书移动端和桌面端**自动多端一致**，但**卡片设计是我们做的客户端工作量**
- 演示时强调："飞书卡片是我们设计的 GUI Co-pilot；卡片在多端原生同步是飞书生态的能力"

**当前决定**：放到 timebox 末尾的 stretch 时段（见 §八）。核心 MVP 跑通且无重大 bug 才做；否则跳过。

### 6.2 GUI 仪表盘缺失

→ 通过 §6.1 的飞书卡片仪表盘补足。

### 6.3 PPT 生成路径未定

10 小时内最稳的两条路径：

| 路径 | 优点 | 缺点 |
|---|---|---|
| **A. python-pptx 程序化生成 → 上传飞书云文档** | 库成熟、可控性高、模板化方便 | 样式相对朴素 |
| **B. LLM 生成 Markdown → marp/pandoc 转 PPT → 上传** | 速度最快，LLM 直接写 | 样式可能不够汇报级 |
| **C. 飞书"演示文稿"原生 API**（如开放） | 直接落在飞书生态、多端同步零成本 | 是否对外开放未知，需先调研 |

**决策**：按 **C > B > A** 顺序试。开局先花 0.5h 调研飞书演示文稿 API（C，首选）；不可行则 LLM 生成 Markdown → marp/pandoc 转 PPT（B）；再不行用 python-pptx 兜底（A，最稳）。

### 6.4 语音输入

赛道说"文本或语音"——**只做文本即可满足必须项**。语音是 nice-to-have，10 小时内不做。

### 6.5 时间极度紧张

10 小时 + 转型 + 多个新组件，timebox 必须严格执行（见 §八）。任何一项超时都要立即 cut scope。
